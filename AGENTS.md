# Контекст репозитория

Этот репо – набор патчей и скриптов для сборки форка [opencode](https://github.com/anomalyco/opencode). Оригинальный исходный код opencode доступен локально в `/workspace/github/opencode`.

## Структура

- `patches/common/` – патчи, применяемые на обе платформы (linux и windows)
- `patches/linux/` – патчи только для linux-сборки
- `patches/windows/` – патчи только для windows-сборки
- `scripts/` – bash-скрипты сборки и подготовки окружения
- `.github/workflows/build.yaml` – CI: клонирует opencode, применяет патчи, собирает артефакты

## Как работает сборка

1. GitHub Actions клонирует opencode по тегу `OPENCODE_VERSION`
2. Применяет патчи через `scripts/patch.sh`
3. Собирает CLI (`scripts/build-cli.sh`) и desktop-приложение (`scripts/build-desktop.sh`): desktop с v1.15 – это Electron (electron-vite + electron-builder), CLI-ядро встраивается как node-бандл через `packages/desktop/scripts/prepare.ts`; linux – AppImage/deb/rpm, windows – NSIS-инсталлятор, кросс-сборка на Ubuntu через wine
4. Загружает артефакты как GitHub Release (черновик для веток, настоящий релиз для тегов)

## Патчи

Каждый `.diff` в `patches/common/` – это `git diff` относительно оригинального репо opencode. Применяются через `patch -p1`. Порядок применения – алфавитный (по имени файла).

Текущие патчи в `patches/common/`:

- `001-ctrl-enter` – отправка сообщений по `Ctrl-Enter` вместо `Enter` в WebUI и Desktop
- `003-markdown-code-scrollbar` – горизонтальный скроллбар в блоках кода вместо обрезки
- `004-retry-overload-cap` – ограничение задержки retry при overload до 11s, certificate errors как retryable
- `005-server-message-id` – исправление дублирования ответа модели при рассинхроне часов
- `006-tmux-clipboard` – обходное решение для копирования в TUI внутри tmux
- `007-unarchive-sessions` – поддержка разархивирования сессий
- `008-user-message-markdown` – рендер сообщений пользователя как markdown
- `009-timestamp-24h` – временны́е метки сообщений в 24h формате с датой (YYYY-MM-DD HH:mm)
- `010-timeout-continue` – восстановление после сетевого таймаута ответа модели (`TimeoutError: The operation timed out.`): частичный ответ финализируется в истории, добавляется синтетическое user-сообщение с просьбой продолжить, и движок сам пересобирает контекст на следующем шаге; остальные ошибки (429, overload и пр.) обрабатываются штатным ретраем без изменений
- `011-mcp-auto-reconnect` – автоматическое восстановление MCP-соединений: ошибка `listTools` больше не удаляет клиент навсегда, а запускает фоновый реконнект с лесенкой задержек в стиле 004 (1s → +1s каждые 3 попытки → кап 11s, циклический сброс после 36 попыток, без лимита попыток); экспайр сессии remote-серверов (`Session terminated`/404) – немедленный реконнект со сбросом счётчика; `callTool` при экспайре ждёт реконнект (до 30s) и ретраится один раз; кэш `listTools` (TTL 1 час) с инвалидацией по TTL, `ToolListChanged`, смене клиента и disconnect; реконнекты активны только при работающих шагах агента (`MCP.beginStep`/`endStep` в `session/prompt.ts`) и отменяются ручным toggle/`enabled: false`/`needs_auth`
- `012-mcp-status-display` – восстановление отображения MCP-серверов в desktop/web (бэкпорт `4e70eabbcc` из v1.16.0): регрессия `e16bfd745d` (в составе v1.15.13) помещала запрос статуса MCP в `child-store.ts` в батч `useQueries`, где per-query `enabled: mcpEnabled()` не реактивен – запрос оставался выключенным навсегда, `store.mcp` был пуст и серверы не отображались; фикс переводит все четыре запроса на отдельные `useQuery`, ленивость «MCP только для открытых директорий» сохраняется, TUI не затронут

## Правила правки патчей

- Патч должен применяться чистым `patch -p1` без rejects
- Контекстные строки (без `+`/`-`) должны точно совпадать с оригиналом в `/workspace/github/opencode`
- Номера строк в заголовках `@@ ... @@` должны соответствовать реальным после предыдущих изменений в том же файле
- Не трогать строки и комментарии вне scope запроса
- Патч должен содержать только свои собственные изменения – никогда не включать повторно ханки,
  уже присутствующие в предыдущих патчах
- Каждый патч должен применяться поверх всех предыдущих патчей по порядку

### Проверка патча после ручной правки

Не пересчитывать номера строк в заголовках `@@ ... @@` вручную построчно – это источник ошибок. Вместо этого проверять применение `patch -p1` к оригиналу после `reset --hard HEAD` или, если почему-то понадобилось его сохранить, к его `git worktree`

Если нужно поправить заголовок ханка после ручного редактирования содержимого – генерировать его не вручную, а через реальный `diff` (без всяких `git diff`) между чистым оригиналом и отредактированной копией, и переносить итоговые ханки в патч.
